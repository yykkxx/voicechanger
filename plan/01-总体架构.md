# 01 总体架构

## 1. 架构原则

1. **路由、采集、处理、注入解耦**：任何 ROM 专用逻辑只能存在于路由适配层。
2. **唯一资源所有者**：所有 `AudioRecord`、`AudioTrack`、`AudioPolicy`、socket 和唤醒锁均由前台服务持有并按逆序释放。
3. **控制面与音频面分离**：Compose/UI、设置和日志不得进入实时音频线程。
4. **有界延迟优先于不丢帧**：实时通话中不能无限积压；拥塞时丢弃旧帧并记录 discontinuity。
5. **先证明路由，再实现效果**：第一条可验收链路必须是已知波形/原声透传到测试接收端。
6. **失败可见且可恢复**：禁止“服务显示运行但实际没有 PCM”的静默失败。

## 3. 核心组件

### 3.1 `VoiceChangerService`

职责：

- 建立前台通知；
- 校验运行时和特权权限；
- 创建、启动、停止 `AudioPipeline`；
- 响应通知栏停止/静音动作；
- 向 UI 暴露只读状态与指标；
- 在 `onDestroy()`、异常和用户停止时幂等清理；
- 服务运行期间可选择持有 `PARTIAL_WAKE_LOCK`，停止后立即释放。

约束：

- 服务只能从可见 Activity 在用户操作后启动，避免 Android 14+ 的 microphone FGS 启动限制；
- 不依赖 `android:persistent` 或开机自启维持录音；
- 推荐 `START_NOT_STICKY`。异常退出后由用户明确重启，避免后台自动拿麦克风。

### 3.2 `PipelineController`

控制完整生命周期，禁止 UI 直接操作音频对象。

```kotlin
interface PipelineController {
    suspend fun start(config: SessionConfig): StartResult
    suspend fun stop(reason: StopReason)
    suspend fun setMuted(muted: Boolean)
    suspend fun updateEffect(params: EffectParams)
    val state: StateFlow<PipelineState>
    val metrics: StateFlow<RealtimeMetrics>
}
```

上述仅为接口草案；实施时音频帧路径不经过 `StateFlow`。

### 3.3 `RouteBackend` / `RouteSession`

负责 ROM/系统相关路由，不负责变声算法：

```kotlin
interface RouteBackend {
    val id: String
    suspend fun probe(request: RouteRequest): CapabilityReport
    suspend fun open(request: RouteRequest): RouteSession
}

interface RouteSession : AutoCloseable {
    val capture: CaptureEndpoint
    val injector: InjectionEndpoint
    val negotiatedFormat: NegotiatedAudioFormat
    suspend fun start()
    suspend fun stop()
}
```

候选后端及优先级见《02-音频路由设计》。

### 3.4 `AudioPipeline`

数据通路：

```text
CaptureEndpoint
  → InputFormatAdapter
  → input SPSC ring
  → ProcessorEngine
  → output SPSC/jitter ring
  → OutputFormatAdapter
  → InjectionEndpoint
```

附加支路：

- 电平计只消费每秒汇总值，不复制整段音频；
- 可选监听支路必须独立限幅，且只开放给耳机设备；
- 调试 dump 默认关闭，只允许开发构建短时、显式开启。

### 3.5 `ProcessorEngine`

```kotlin
interface ProcessorEngine : AutoCloseable {
    fun configure(format: StreamFormat, params: EffectParams)
    fun process(input: PcmFrame, output: MutablePcmFrame): ProcessResult
    fun update(params: EffectParams)
    fun reset(discontinuity: Boolean)
}
```

实现：

- `PassthroughProcessor`：路由与延迟基线；
- `InternalDspProcessor`：JNI/native 实时变声；
- `LoopbackSocketProcessor`：本地 TCP 全双工处理；
- `MuteProcessor`：故障安全输出。

参数更新使用原子快照，在帧边界生效；不得在处理线程重建大对象。

### 3.6 `CapabilityProbe`

生成结构化报告：

- 应用路径、system/privileged flags；
- 权限 grant 与 app-op；
- 输入/输出设备的 id、type、address、支持格式；
- 虚拟设备地址是否存在；
- AudioPolicy 注册试探结果及异常；
- 当前选中的后端与拒绝其他后端的原因；
- SELinux 拒绝只能提示用户抓系统日志，应用自身不尝试放宽策略。

报告允许复制/导出文本，但不包含 PCM 或敏感语音内容。

## 4. 服务状态机

```text
Idle
  └─ start → Checking
Checking
  ├─ invalid → Error
  └─ valid   → PreparingRoute
PreparingRoute
  ├─ failed  → Error
  └─ ready   → StartingAudio
StartingAudio
  ├─ failed  → Stopping → Error
  └─ success → Running.Internal / Running.External
Running.*
  ├─ mute/unmute → Running.*
  ├─ recoverable fault → Recovering
  ├─ mode/config change → Stopping → Checking
  └─ stop → Stopping → Idle
Recovering
  ├─ recovered → Running.*
  ├─ timeout → Error
  └─ stop → Stopping → Idle
```

原则：

- `start`、`stop` 必须串行化且幂等；
- 切换处理模式首版采用短暂停流重建，不冒险热换底层路由；
- 任何部分启动失败都执行完整回滚；
- `Error` 保存稳定错误码、用户提示和诊断上下文，而不是只保存异常字符串。

建议错误域：`PERMISSION_*`、`ROUTE_*`、`CAPTURE_*`、`INJECT_*`、`DSP_*`、`SOCKET_*`、`SYSTEM_INTERRUPTION`。

## 5. 实时线程与缓冲模型

### 5.1 标准帧

- 采样率：48,000 Hz；
- 通道：1；
- 编码：PCM 16-bit little-endian；
- 帧长：10 ms，即 480 sample、960 byte；
- 时间戳：采集单调时钟 `elapsedRealtimeNanos`；
- 序号：无符号递增 32-bit，回绕按模运算处理。

设备边界若要求 stereo，则每帧转换成 480 × 2 sample；网络内部仍默认 mono。

### 5.2 线程建议

- `capture-thread`：阻塞读 AudioRecord，写 input ring；
- `process-thread`：本地 DSP，或外部模式下负责入站帧编排；
- `socket-tx` / `socket-rx`：仅外部模式存在；不能同步等待每帧返回；
- `inject-thread`：从 output ring 读并写 AudioTrack；
- `control-scope`：协程串行处理启动、停止、参数和诊断。

音频相关线程申请音频优先级，但必须处理申请失败。严禁在这些线程执行：对象频繁分配、Compose 状态更新、文件 I/O、DNS、阻塞式重连、大量日志。

### 5.3 队列策略

- 所有队列固定容量，建议从 6 帧（60 ms）开始实测调优；
- input ring 满：丢最旧帧，标记 discontinuity，确保采集不被网络拖死；
- output ring 空：写零帧，递增 underrun，不重复旧人声；
- 外部返回过晚：丢弃已过播放截止时间的帧；
- 每次 discontinuity 通知 DSP 重置需要连续历史的状态。

### 5.4 延迟预算（不含目标应用编码/网络）

| 环节 | 内部模式目标 | 外部模式目标 |
|---|---:|---:|
| 采集及系统缓冲 | 10–25 ms | 10–25 ms |
| 队列和格式适配 | 5–15 ms | 10–30 ms |
| 处理 | 5–20 ms | 本地 socket 往返 + 处理 10–35 ms |
| 注入及系统缓冲 | 10–30 ms | 10–30 ms |
| 端到端 P95 目标 | ≤100 ms | ≤130 ms |

最终以目标 ROM 的 loopback 测量为准，不以 Java 调用耗时替代声学/波形测量。

## 6. UI 与设置边界

### 6.1 页面

- **主页**：开始/停止、静音、处理模式、预设、目标应用、当前路由状态；
- **效果页**：音调、共振峰、强度、降噪/限幅等；
- **外部处理页**：host（首版固定 loopback）、port、连接状态、往返和队列延迟；
- **路由诊断页**：权限、设备、后端、错误与一键复制报告；
- **高级设置**：缓冲、输入源、故障策略、手动路由后端。

### 6.2 数据持久化

使用 DataStore 保存低频配置：模式、端口、效果参数、目标包名、故障策略。运行状态和瞬时指标只保存在内存，不用数据库保存每帧或高频指标。
