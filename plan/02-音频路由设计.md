# 02 音频路由设计

## 1. 路由目标与事实核对

本项目真正需要的链路是：

```text
本应用采集物理麦克风
  → 处理 PCM
  → 系统/厂商注入端
  → 目标应用的 AudioRecord 读到处理后 PCM
```

这不同于“捕获游戏播放声音”：

```text
目标应用 AudioTrack
  → AudioMix LOOP_BACK
  → 本应用 AudioRecord
```

`/sdcard/yykkxx/语音路由.md` 中 `USAGE_GAME + ROUTE_FLAG_LOOP_BACK + createAudioRecordSink()` 的示例属于第二种链路，可用于抓取播放音频，但不能直接完成麦克风变声回注。实现时必须避免把“成功捕获游戏声音”误判为“成功替换麦克风”。

还需明确：

- `AudioTrack.preferredDevice = virtualOut` 只表示请求向该输出设备播放；
- `AudioRecord.preferredDevice = virtualIn` 只表示请求从该输入设备采集；
- 两个地址同时存在并不自动证明它们在 HAL 内部首尾相连；
- AOSP remote submix 是环回基础设施，本身也不是面向任意第三方录音客户端的通用虚拟麦克风。

因此，路由层采用“能力探测 + 多后端 + 已知波形验证”，不硬编码单一路径。

## 2. 路由抽象

### 2.1 请求模型

`RouteRequest` 至少包含：

- 目标应用 packageName 与当前 UID；
- 目标 capture preset（未知时为 AUTO）；
- 输入设备偏好（内置麦克风、有线、USB、Bluetooth）；
- 内部标准格式；
- 是否开启安全监听；
- 手动指定后端或 AUTO；
- 是否允许影响同 UID/同 capture preset 的其他录音客户端。

### 2.2 能力报告

每个后端返回：

- `SUPPORTED`、`DEGRADED`、`UNSUPPORTED`；
- 缺失权限/API/设备；
- 可匹配粒度：UID、capture preset、全局；
- 可用格式与估算延迟；
- 是否要求目标应用在策略注册后重新打开 AudioRecord；
- 风险说明和可执行诊断建议。

AUTO 只选择通过主动验证的后端，不以“枚举到了设备”作为可用结论。

## 3. 后端设计

### 3.1 `PolicyRecorderMixBackend`（首选候选）

目标：注册 **recorder 类型**的 `AudioMix`，按当前 ROM 支持情况匹配目标 UID/capture preset，并取得与 policy mix 关联的注入 `AudioTrack`（例如系统版本提供的 track-source 能力），将处理后的 PCM 送入匹配的录音路径。

实施要点：

1. 隔离所有 `android.media.audiopolicy` system API 调用；
2. 优先按目标 UID 限定，无法按 UID 时才退化为 capture preset；
3. 使用 loopback/injection 所需 route flags，而不是照搬 player mix 的 `USAGE_GAME` 规则；
4. 检查注册返回值、mix registration/address、track 初始化状态；
5. 注册策略后要求测试接收端重新创建 AudioRecord，以覆盖“不热迁移既有录音流”的 ROM；
6. 停止时先送静音、停止 track，再注销 policy；
7. system API 在不同 Android 版本可能签名不同，适配代码集中在版本化 facade 中。

关键验证：测试接收应用录制 `MIC`/`VOICE_COMMUNICATION` 时，能否收到本应用写入的 1 kHz 标记音，且物理麦克风敲击声不直接穿透。

### 3.2 `OplusVirtualAudioBackend`（ColorOS 候选）

根据输入文档，目标设备可能暴露：

- 输出地址：`127.0.0.1`～`127.0.0.5`；
- 输入地址：`127.0.1.1`；
- 预计格式：PCM 16-bit、48 kHz、stereo；
- HAL：`libvirtualaudio.so`。

探测规则：

1. 同时记录 id、type、productName、address、sampleRates、channelCounts、encodings；
2. address 作为重要特征，但不只靠 address；允许高级设置手动选择；
3. 分别验证每个 virtual out，不假定 `.1` 是正确通道；
4. 用唯一测试波形验证 virtual out 与目标输入路径的真实关系；
5. 如果需要 framework 路由策略把目标 UID 指向 `Virtual Host In`，该策略也属于本后端，不把 `preferredDevice` 当作完整方案；
6. 路由格式固定 stereo 时，在注入边界进行 mono→stereo，不让 DSP 为 ROM 格式负责。

可能结果：

- **完整支持**：virtual out 写入后可通过 policy 路由给目标 recorder；
- **仅管道支持**：本应用可以一端写、一端读，但无法替换第三方输入；
- **仅枚举支持**：设备存在但 open/start 失败；
- **不支持**：ROM 无该模块或地址变化。

只有第一种结果可作为生产后端，第二/三种只能用于诊断。

### 3.3 `RemoteSubmixBackend`（AOSP 候选/诊断）

remote submix 适合建立受 AudioPolicy 控制的环回通道。该后端负责验证：

- ROM 是否启用 remote-submix module；
- policy 是否能创建所需 recorder mix；
- 是否能把目标录音流匹配到注入源；
- 使用地址/tag 后数据是否真正到达目标。

如果只能抓取系统播放而不能给目标 AudioRecord 注入，则标记为 `DEGRADED_CAPTURE_ONLY`，不能在 UI 中显示为“变声路由已就绪”。

### 3.4 `MonitorOnlyBackend`（开发与降级）

链路为 `麦克风 → 处理 → 耳机 AudioTrack`，不尝试影响第三方应用。用途：

- 验证采集、DSP、socket 和延迟；
- 普通安装包开发；
- 路由失败时给出可理解的演示模式。

安全限制：检测到扬声器时默认禁止监听，必须由用户显式确认，防止啸叫。

## 4. 后端选择顺序

AUTO 建议顺序：

1. 通过主动注入测试的 `PolicyRecorderMixBackend`；
2. 通过主动注入测试的 `OplusVirtualAudioBackend`；
3. 通过主动注入测试的 `RemoteSubmixBackend`；
4. `MonitorOnlyBackend`，并明确标识“不向目标应用注入”。

可在特定 ColorOS 设备测试后调整前两项优先级。探测结果以 ROM build fingerprint 为 key 缓存，但系统升级或权限变化后必须失效重测。

## 5. 输入采集

### 5.1 音频源优先级

建议依次探测：

1. `UNPROCESSED`（设备声明支持时）；
2. `VOICE_RECOGNITION`（通常较少通话链路处理）；
3. `MIC`；
4. `VOICE_COMMUNICATION` 仅在确实需要系统 AEC/NS 且测试无双重处理时使用。

输入通常为 mono。使用 `AudioRecord.getMinBufferSize()` 作为下限，不直接把它当成低延迟最佳值；实际 buffer 需覆盖若干 10 ms 帧并通过 underrun/overrun 调优。

### 5.2 设备变化

监听设备增删和路由变化：

- 有线/USB 麦克风切换可选择自动重建会话；
- Bluetooth SCO/窄带可能只有 8/16 kHz，必须经过 resampler；
- 首版可将 Bluetooth 标记实验功能，优先保证内置、有线和 USB；
- 重建期间输出静音，不能把旧缓冲写入新会话。

## 6. 格式协商

内部处理固定为 48 kHz mono S16LE，边界做适配：

```text
AudioRecord native format
   → decode/channel mix/resample
   → 48k mono S16LE
   → processor
   → 48k mono S16LE
   → resample/channel expand
   → injection native format
```

选择原则：

- 能原生打开 48 kHz 时不重采样；
- 厂商虚拟端要求 stereo 时复制 mono 到 L/R；
- 不接受“API 对象创建成功但 state 未初始化”；
- 记录 requested format 与 actual format；
- 重采样器必须流式保存相位，并在 discontinuity 时重置。

## 7. 启动时序

推荐顺序：

1. UI 已获取 `RECORD_AUDIO`，从前台发起启动；
2. 服务立即建立前台通知；
3. 校验 privileged flag、权限、app-op 和麦克风隐私开关；
4. 解析目标 package→UID，运行/读取 capability probe；
5. 选定后端并注册策略；
6. 创建 injection endpoint，写少量零帧预热但不泄露到物理扬声器；
7. 创建 capture endpoint；
8. 创建 processor 与所有固定缓冲；
9. 启动 injection，再启动 capture/processing；
10. 等待有效输入和成功写入，状态才变为 `Running`；
11. 提示用户让目标应用在此后打开或重开麦克风；
12. 根据接收侧/系统指标确认路由，而非仅依据线程存活。

目标应用已经持有 AudioRecord 时，系统不一定把它热切换到新策略；首版 UI 应明确提示“先启动变声器，再开启目标应用麦克风”。

## 8. 停止与恢复

停止顺序：

1. 状态进入 `Stopping`，拒绝新参数/启动命令；
2. 注入 20–50 ms 零帧并停止采集；
3. 停处理和网络线程，清空队列；
4. 停止并释放 injection/capture；
5. 注销 AudioPolicy、移除 preferred device/listener；
6. 恢复此前的 AudioManager mode/communication device（若曾修改）；
7. 释放唤醒锁和前台通知；
8. 清零 PCM 缓冲。

所有步骤均允许重复执行。任何启动失败也调用同一清理路径。

## 9. 运行期冲突处理

- **电话/VoIP 抢占**：收到录音静默、设备变化或 focus/telephony 回调后进入 `Recovering`，默认静音并提示；
- **另一个录音客户端**：Android 并发录音可能让其中一方拿到 silence；诊断页显示 active recording configuration（API/权限允许时）；
- **麦克风隐私开关**：立即反映为明确错误，不持续空转；
- **目标应用退出**：可保持短时间等待，超时后停止或进入待机，由用户设置决定；
- **服务被杀**：framework 通常会清理进程持有的 policy，但下次启动仍先做残留状态探测；
- **物理扬声器反馈**：注入路径不得同时默认播放到 speaker。

## 10. 路由 PoC 的硬性通过条件

在开始正式变声算法前，必须全部满足：

1. `pm path` 与 package flags 证明应用为 privileged；
2. `MODIFY_AUDIO_ROUTING` 实际 `granted=true`；
3. 注册/注销策略连续 20 次无残留和崩溃；
4. 测试接收应用能录到注入的已知 1 kHz/伪随机标记波形；
5. 标记波形序列可证明数据来自注入，而非扬声器声学回录；
6. 停止后测试接收应用恢复正常物理麦克风；
7. 整个测试在 SELinux Enforcing 下完成。

若第 4 条失败，项目仍可继续做监听型变声器，但不能宣称能给第三方语音应用提供虚拟麦克风。
