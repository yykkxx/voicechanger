# 03 处理引擎与本地端口协议

## 1. 统一处理接口

内部 DSP 和本地端口处理必须看到相同的帧模型，路由层不感知处理方式：

```text
StreamFormat
- sampleRate = 48000
- channels = 1
- encoding = PCM_S16LE
- frameDurationMs = 10
- samplesPerFrame = 480

PcmFrame
- sequence: UInt32
- captureTimestampUs: UInt64 (monotonic)
- flags: discontinuity / muted / endOfStream
- payload: 960 bytes
```

实现中不应每 10 ms 创建 Kotlin `data class` 和 `ByteArray`；上面只是逻辑模型。实际使用固定帧池、直接缓冲区或预分配的 `ShortArray` 槽位。

## 2. 内部处理模式

### 2.1 首版处理链

```text
输入
 → DC blocker / 高通（可选）
 → noise gate 或轻量降噪（可选）
 → pitch shift
 → formant shift
 → 音色效果（机器人声等，可选）
 → limiter / soft clip
 → 输出
```

实现顺序：

1. `PassthroughProcessor`：验证位精度、帧序、延迟；
2. gain + limiter：验证参数热更新；
3. pitch shift；
4. formant shift；
5. 降噪、机器人声、混响等附加效果。

不要在路由尚未通过时引入 AI 声线转换模型。AI 模型通常带来更高的帧窗口、算力、发热和许可风险，可作为后续独立 processor。

### 2.2 Kotlin 与 Native 边界

建议：

- Kotlin 管生命周期、路由、状态和缓冲调度；
- C/C++ 管高频 DSP 核心；
- JNI 使用复用的 direct buffer 或批量帧，避免每帧复制/分配；
- 底层 AudioPolicy 创建的 Java `AudioRecord/AudioTrack` 继续由 Kotlin 包装，不为追求“全 Native”破坏路由能力；
- native processor 只接受标准 PCM，不直接持有 Android UI/Service 对象。

第三方 DSP 库引入前检查许可证、ABI（至少 arm64-v8a）和实时安全性。GPL/商业双许可库不能在未确认发布方式前直接纳入。

### 2.3 参数与预设

`EffectParams` 建议包括：

- `pitchSemitones`；
- `formantRatio`；
- `mix`（dry/wet）；
- `inputGainDb`、`outputGainDb`；
- `noiseGateThresholdDb`；
- `limiterEnabled`；
- 效果专用参数。

参数在帧边界读取不可变快照；音调、增益等连续参数在 20–50 ms 内平滑，避免拉链噪声。预设只保存参数，不直接保存处理器内部状态。

## 3. 外部本地端口模式

### 3.1 角色

- Android 应用：TCP client、采集方和最终注入方；
- 本地处理程序：TCP server，监听 loopback，接收 `PCM_INPUT`，返回 `PCM_OUTPUT`；
- 默认地址：`127.0.0.1:18765`；端口可配置；
- 首版只允许 IPv4/IPv6 loopback，不允许局域网或公网地址。

选 TCP 的原因：localhost 上无须自行处理 UDP 丢包，开发和协议解析更简单。协议仍采用帧序号、时间戳和有界队列，以避免 TCP 背压造成无限延迟。若后续模型需要共享内存/Unix domain socket，可新增 transport，而不改变 processor 接口。

### 3.2 不能采用逐帧同步 RPC

错误方式：发送一帧 → 阻塞等待对应返回 → 再采下一帧。它会把处理抖动直接叠加到采集，并容易产生 underrun。

正确方式：

```text
capture → bounded queue → socket-tx  ───────► server
inject ← jitter/output queue ← socket-rx ◄─── server
```

TX/RX 全双工并行；最多允许有限 in-flight 帧。超过上限时淘汰旧帧并发送 discontinuity 信息，不扩大缓存。

## 4. TCP 二进制协议 VCP/1

### 4.1 通用包头

固定 24 byte，整数为 network byte order（big-endian）：

| Offset | 长度 | 字段 | 说明 |
|---:|---:|---|---|
| 0 | 4 | magic | ASCII `VCP1` |
| 4 | 1 | version | `1` |
| 5 | 1 | type | 消息类型 |
| 6 | 2 | flags | bit flags |
| 8 | 4 | sequence | PCM 序号；控制消息可为 0 |
| 12 | 8 | timestampUs | 单调时间；无意义时为 0 |
| 20 | 4 | payloadLength | 后续 payload byte 数 |

限制：

- 单包 payload 上限 64 KiB；
- magic/version/长度非法立即断开；
- PCM payload 为 **little-endian signed 16-bit**，与包头字节序不同；
- PCM 包不含 WAV header；
- parser 必须支持 TCP 拆包和粘包。

### 4.2 消息类型

| 值 | 名称 | 方向 | Payload |
|---:|---|---|---|
| `0x01` | `HELLO` | App→Server | UTF-8 JSON 能力请求 |
| `0x02` | `HELLO_ACK` | Server→App | UTF-8 JSON 协商结果 |
| `0x03` | `START` | App→Server | UTF-8 JSON 参数/预设 |
| `0x04` | `STOP` | App→Server | 可空 |
| `0x10` | `PCM_INPUT` | App→Server | S16LE PCM |
| `0x11` | `PCM_OUTPUT` | Server→App | S16LE PCM |
| `0x12` | `PARAMS` | App→Server | UTF-8 JSON 参数增量 |
| `0x20` | `STATS` | 双向 | UTF-8 JSON 低频统计 |
| `0x30` | `PING` | 双向 | 可空/nonce |
| `0x31` | `PONG` | 双向 | 原样 nonce |
| `0x7F` | `ERROR` | 双向 | UTF-8 JSON 错误 |

### 4.3 Flags

- bit 0 `DISCONTINUITY`：此前发生丢帧，处理器应重置连续状态；
- bit 1 `MUTED`：payload 为静音或应按静音处理；
- bit 2 `END_OF_STREAM`；
- 其他位保留，收到未知位应忽略而非断开。

### 4.4 HELLO 示例

App 请求：

```json
{
  "client": "android-voice-changer",
  "protocol": 1,
  "formats": [
    {
      "sampleRate": 48000,
      "channels": 1,
      "encoding": "pcm_s16le",
      "frameSamples": 480
    }
  ],
  "maxInFlightFrames": 6
}
```

Server 响应：

```json
{
  "accepted": true,
  "format": {
    "sampleRate": 48000,
    "channels": 1,
    "encoding": "pcm_s16le",
    "frameSamples": 480
  },
  "algorithmicDelayFrames": 2,
  "server": "local-dsp/1.0"
}
```

首版可只接受标准格式；不支持时返回 `accepted=false` 和稳定错误码。JSON 只用于低频控制，音频永远使用二进制 payload。

### 4.5 PCM 序号规则

- App 给每个 `PCM_INPUT` 分配连续 sequence；
- Server 返回的 `PCM_OUTPUT.sequence` 应表示该输出主要对应的输入序号；
- 固定 lookahead 的 server 在 HELLO_ACK 声明 `algorithmicDelayFrames`；
- Server 不得为了补齐丢失序号无限等待；应返回静音/插值或带 `DISCONTINUITY` 的下一帧；
- 输出帧样本数通常固定 480，若算法一次返回多帧，应拆成多个协议包。

## 5. 连接生命周期

```text
Disconnected
 → Connecting (1 s timeout)
 → Handshaking (2 s timeout)
 → Ready
 → START
 → Streaming
 → STOP
 → Closing
```

Streaming 期间：

- 每 2 秒无流量时发送 PING；
- 500 ms 没有任何有效输出即认为音频超时，进入故障策略；
- socket 写阻塞超过预算时丢待发送旧帧，而不是阻塞 capture；
- 重连退避建议 250 ms、500 ms、1 s、2 s、最高 5 s；
- 重连成功后先发 HELLO/START，再发送带 `DISCONTINUITY` 的新实时帧；绝不重放积压人声。

默认故障策略为：

1. 立即向注入端持续写静音；
2. UI/通知显示“外部处理器断开”；
3. 后台有限重连；
4. 超过可配置期限后停止会话。

“原声旁路”必须由用户显式开启，因为自动泄露未变声语音可能违背用户预期。

## 6. 外部处理器责任

Server 必须：

- 只监听 loopback；
- 连续消费输入，不能依赖任意大 TCP 缓冲；
- 保持输出实时性，过期帧宁可丢弃；
- 对每条连接隔离 DSP 状态；
- START 时清空旧状态，STOP/断开时释放；
- 返回稳定错误码而非只关闭连接；
- 不默认把 PCM 写入磁盘。

建议在项目后期于 `tools/local_processor_reference/` 提供一个参考 server（先做纯透传和可控延迟），以便协议联调；它不是 Android APK 的运行时依赖。

## 7. 抖动、时钟与延迟统计

本机 TCP 通常稳定，但处理器可能抖动。输出队列建议初始 3 帧（30 ms），可在 2–6 帧范围内调节。统计：

- capture frames / dropped input；
- socket bytes / reconnect count；
- in-flight frames；
- output late/drop/underrun；
- DSP processing P50/P95/P99；
- capture timestamp 到 injection write 的 P50/P95；
- 当前估算总缓冲时长。

单调时钟只用于同一设备进程间的相对统计。若本地 server 运行在 Android 同一内核命名空间，时间戳仍不应假定不同语言运行时 epoch 完全一致；核心延迟由 App 依据 sequence 和本地发送/接收时刻计算。

## 8. 安全与健壮性

- v1 不开放非 loopback 地址，因此不引入 TLS；
- Manifest 仍需 `INTERNET` 才能创建 socket；
- 校验所有长度、JSON 大小、数值范围和消息方向；
- 限制一条会话、有限队列和有限日志，防止本地恶意服务耗尽内存；
- 不把 socket 收到的数据直接传给 JNI 而不校验对齐和样本数；
- 在通知中明确本地程序可访问麦克风流；
- 将来若开放 LAN，必须设计认证、加密、重放保护和明确授权，不能复用无认证 v1 默认配置。
