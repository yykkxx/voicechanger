# 04 权限、部署与安全

## 1. 两类权限必须分开处理

### 1.1 用户/普通权限

| 权限 | 用途 | 处理方式 |
|---|---|---|
| `android.permission.RECORD_AUDIO` | 物理麦克风采集 | 运行时申请；拒绝则不启动 |
| `android.permission.FOREGROUND_SERVICE` | 前台服务 | Manifest |
| `android.permission.FOREGROUND_SERVICE_MICROPHONE` | Android 14+ 麦克风 FGS | Manifest；从可见界面启动 |
| `android.permission.FOREGROUND_SERVICE_MEDIA_PLAYBACK` | 持续向注入/监听 AudioTrack 写入时的服务类型 | Manifest，是否必需在 PoC 后确认 |
| `android.permission.POST_NOTIFICATIONS` | Android 13+ 通知体验 | 运行时申请；FGS 仍需合法通知 |
| `android.permission.INTERNET` | 连接 localhost TCP server | Manifest |
| `android.permission.WAKE_LOCK` | 活跃会话防止 CPU 休眠 | Manifest；只在运行期持有 |
| `android.permission.MODIFY_AUDIO_SETTINGS` | 合法音频设置 | Manifest |

服务声明预计使用：

```xml
<service
    android:name=".service.VoiceChangerService"
    android:exported="false"
    android:foregroundServiceType="microphone|mediaPlayback" />
```

如果最终没有常规播放型职责，应根据真机行为缩小 service type，而不是无条件声明更多类型。

### 1.2 特权权限

| 权限 | 计划用途 | 备注 |
|---|---|---|
| `android.permission.MODIFY_AUDIO_ROUTING` | 注册 AudioPolicy、修改受控路由 | 核心前提 |
| `android.permission.CAPTURE_AUDIO_OUTPUT` | 播放捕获/诊断或特定 policy 路径 | 若最终链路不使用则移除 |

是否还需 ROM 专用或其他 system permission，只能根据实际 API 抛出的 `SecurityException` 和系统源码/日志决定。不得预先申请大批无关特权权限。

## 2. Android 14/15 前台服务约束

当前模板 `targetSdk=35`，因此设计必须按新规则执行：

1. 在 Manifest 声明准确的 foreground service type；
2. 声明对应的 `FOREGROUND_SERVICE_*` 权限；
3. 先由前台 Activity 获得 `RECORD_AUDIO`；
4. 用户点击开始后调用 `startForegroundService()`；
5. 服务在系统时限内调用 `startForeground()`；
6. 不从 `BOOT_COMPLETED` 静默启动麦克风服务；
7. 麦克风权限被撤销或隐私开关关闭后立即进入错误/停止状态。

即使应用是 privileged，也不应假定所有前台服务与隐私限制自动豁免。

## 3. priv-app 与权限白名单

输入文档提出通过 Magisk 将 APK 挂载到 `/system/priv-app/`。规划中的模块结构：

```text
voice_changer_priv/
├── module.prop
├── system/
│   ├── priv-app/
│   │   └── VoiceChanger/
│   │       └── VoiceChanger.apk
│   └── etc/
│       └── permissions/
│           └── privapp-permissions-voice-changer.xml
└── sepolicy.rule              # 仅确有 denial 时添加
```

白名单中的 package 必须与最终 `applicationId` 完全一致：

```xml
<?xml version="1.0" encoding="utf-8"?>
<permissions>
    <privapp-permissions package="APP_ID">
        <permission name="android.permission.MODIFY_AUDIO_ROUTING" />
        <permission name="android.permission.CAPTURE_AUDIO_OUTPUT" />
    </privapp-permissions>
</permissions>
```

注意事项：

- `APP_ID` 在开始实现前锁定；当前模板的 `com.java.myapplication` 不能用于正式部署；
- APK 和 privapp allowlist 应落在系统认可、相互匹配的分区覆盖路径；
- “位于 priv-app”与“权限已授予”要分别验证，不能只看文件存在；
- Android 版本/ROM 对 allowlist enforcement 有差异，以 `dumpsys package` 的实际 grant 为准；
- 某些 API 除 permission 外仍可能检查调用 UID、签名或角色，必须由 PoC 验证；
- 更新 APK 后重启并重新检查，避免旧包路径/数据覆盖测试结果。

## 4. 部署后检查清单

将 `APP_ID` 替换为最终包名：

```bash
pm path APP_ID
# 路径应显示在 priv-app 覆盖结果中

dumpsys package APP_ID | grep -iE "flags|PRIVATE_FLAG_PRIVILEGED|SYSTEM"

dumpsys package APP_ID | grep -E \
  "MODIFY_AUDIO_ROUTING|CAPTURE_AUDIO_OUTPUT|RECORD_AUDIO"

appops get APP_ID RECORD_AUDIO

# 路由启动后
dumpsys media.audio_policy
dumpsys media.audio_flinger
```

应用诊断页也应展示这些结论，但 shell 输出仍是排障的权威证据之一。

## 5. System API / Hidden API 策略

`AudioPolicy/AudioMix` 的部分能力在不同 API 级别可能是 public、system API 或隐藏接口。设计约束：

1. 先检查 compileSdk 35 SDK stub 是否直接暴露所需 API；
2. 不能编译时，仅在 `audio/route/platform/` 中引入最小 system stub 或版本 facade；
3. `compileOnly` stub 不打包到 APK，避免覆盖 framework 类；
4. 反射只能作为隔离适配方案，并在启动时做存在性/签名检查；
5. privileged 身份不等于所有 hidden API 都必然可调用；以目标 ROM 的 hidden-api policy 和运行结果为准；
6. 禁止把某台设备提取的完整 `framework.jar` 当普通实现依赖打进应用；
7. 每个 API 分支按 SDK_INT、方法签名和能力测试选择，不能只按品牌字符串选择。

## 6. SELinux 原则

默认在 `Enforcing` 下开发和验收。只有出现明确的 `avc: denied` 且能对应到本应用操作时，才新增最小规则。

排查：

```bash
dmesg | grep -i "avc: denied" | grep -iE "audio|priv_app|APP_ID"
logcat -b all | grep -iE "avc: denied|AudioPolicy|AudioFlinger"
```

规则原则：

- 不切换全局 Permissive；
- 不使用大范围 `allow * * * *`；
- 每条规则记录触发操作、ROM build 和必要性；
- 先确认失败不是权限、API 参数或设备格式错误；
- `sepolicy.rule` 应是设备/版本特定部署资产，不与通用 APK 逻辑耦合。

## 7. 用户隐私和可见性

该应用持续访问麦克风，必须满足：

- 只能由用户显式点击开始；
- 常驻前台通知显示“正在采集并变声”、当前模式和停止按钮；
- 主界面始终显示麦克风、处理器、注入三段状态；
- 默认不保存 PCM、不生成录音文件；
- 日志只记录数值指标和错误，不记录 payload；
- 外部处理模式明确提示 PCM 会交给本机另一个进程；
- 外部处理失败默认静音，避免无意暴露原声；
- 停止时清空可复用缓冲中的有效样本；
- 崩溃后的下次启动先确认没有残留策略，再允许新会话；
- 监听功能默认关闭，并优先限制到耳机，避免声学回授。

## 8. 本地端口安全

首版：

- host 只接受 `127.0.0.1`、`::1` 或明确识别为 loopback 的地址；
- 不接受域名，避免 DNS 与解析绕过；
- 单连接、固定最大 payload、固定队列上限；
- handshake 超时，非法包立即断开；
- UI 显示连接的本地端口和 server 标识；
- 不把调试开关设计成一键监听 `0.0.0.0`。

未来若支持 LAN，视为新威胁模型，必须另行加入双向认证/授权和加密，不能只把 host 输入框放开。

## 9. 包名、签名与构建变体

建议在实现前确定正式 `applicationId`，例如 `com.<owner>.voicechanger`。构建可分：

- `debug`：普通安装也可运行 MonitorOnly 和协议/DSP 测试；
- `privilegedDebug`：用于 Magisk 路由 PoC，保留详细诊断；
- `release`：关闭 PCM dump 与过量日志，固定签名并生成对应 Magisk 模块。

privileged 权限是否授予主要由 ROM 的 permission 定义、安装分区和 allowlist 决定，但稳定签名仍关系到应用升级和数据保留。发布后不得随意更换签名。

## 10. 不采用的做法

- 不调用或破解厂商 `MagicVoiceService` 私有签名/握手；
- 不全局关闭 SELinux；
- 不假装普通 APK 已拥有 `MODIFY_AUDIO_ROUTING`；
- 不在没有通知的后台偷偷录音；
- 不将公网地址伪装成本地处理模式；
- 不在故障时无限缓存用户语音等待 server 恢复。
