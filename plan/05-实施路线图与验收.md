# 05 实施路线图与验收

## 1. 总体策略

首要风险不是 Compose UI，也不是音调算法，而是“目标 ROM 能否把处理后的 PCM 注入第三方录音路径”。开发顺序必须围绕这一点：

```text
设备/权限可行性
 → 已知音验证注入
 → 原声低延迟透传
 → 前台服务工程化
 → 内部 DSP
 → 本地端口
 → UX、稳定性和发布
```

每阶段都有退出条件。未通过的阶段不得用后续功能掩盖。

## 2. Phase 0：冻结需求与建立基线

任务：

- 确定正式 applicationId、应用名和首要目标设备；
- 记录 build fingerprint、Android/ColorOS 版本、CPU ABI；
- 确定首要目标语音应用 packageName；
- 确认 Magisk/root 是部署前提；
- 保留当前 Compose 模板可构建基线；
- 增加架构中的稳定错误码与日志规范草案。

退出条件：

- `./gradlew assembleDebug` 成功；
- 目标设备/ROM/目标应用有明确记录；
- package ID 不再使用模板值。

## 3. Phase 1：路由能力 Spike（最高优先级）

### 3.1 最小生产物

- 权限/privileged 诊断页或命令输出；
- 音频设备枚举器；
- policy 注册/注销探针；
- 生成 1 kHz + 伪随机标记序列的注入器；
- 一个独立测试接收端（可放在 `tools/route_receiver_test/`），使用 AudioRecord 统计频谱/序列；
- 各候选 `RouteBackend` 的最小实验实现；
- Magisk 模块骨架与 privapp allowlist。

测试接收端非常重要：直接拿商业语音 App 听感测试无法区分数字注入、声学回录、系统降噪和 App 编码问题。

### 3.2 实验矩阵

逐项记录结果：

| 实验 | 输入 | 预期证据 |
|---|---|---|
| 权限 | 注册空 AudioPolicy | 成功返回，dumpsys 可见 |
| 厂商设备 | 向每个 `127.0.0.x` 写标记音 | 明确哪一端能读/谁能读 |
| recorder mix | 向 policy track source 写标记音 | 测试 receiver 数字域收到 |
| remote submix | 写入/读取标记音 | 判断仅 loopback 还是可注入目标 |
| 清理 | 连续启动停止 20 次 | 无残留 mix、设备恢复 |
| 目标限定 | 两个 receiver/不同 UID | 验证是否只影响目标 UID |

### 3.3 硬退出条件

至少一个生产候选后端满足《02》中的路由 PoC 七项条件。否则必须作产品决策：

- 降级为“耳机监听型变声器”；或
- 针对目标 ROM 开发更深的系统组件/HAL 修改；或
- 暂停第三方虚拟麦克风目标。

不能在路由未通过时宣称核心功能可行。

## 4. Phase 2：实时透传核心与前台服务

任务：

- 实现 `VoiceChangerService` 与通知；
- 完成状态机和幂等启动/停止；
- 实现 Capture/Injection endpoint；
- 实现固定帧池、SPSC ring、格式适配；
- 接入 `PassthroughProcessor` 和 `MuteProcessor`；
- 展示 RMS、丢帧、underrun、当前设备/后端；
- 处理中断、麦克风隐私开关、设备断开；
- 默认不开放监听扬声器。

退出条件：

- 麦克风→透传→目标 receiver 连续运行 30 分钟；
- 启停 20 次无崩溃、无 policy/AudioRecord/AudioTrack 泄漏；
- 屏幕关闭后服务继续且通知可停止；
- 强制停止/权限撤销后路由恢复；
- 延迟测量机制可用，P95 有基线数据。

## 5. Phase 3：内部 DSP

任务：

1. gain + limiter；
2. pitch shift；
3. formant shift；
4. 参数无爆音平滑；
5. 预设系统；
6. 必要时增加 noise gate/降噪；
7. Native 崩溃保护和 ABI 构建；
8. 完成第三方库许可证审查。

质量测试：

- 正弦扫频、脉冲、静音、满幅、削波输入；
- 频率偏移是否符合 semitone 参数；
- 10 分钟参数持续滑动无崩溃/明显爆音；
- DSP 不产生 NaN/溢出（浮点内部时）；
- CPU、温度、内存和电量记录；
- 与系统 AGC/NS 组合不存在明显 pumping 或双重处理。

退出条件：

- 内部模式端到端 P95 目标 ≤100 ms（不含目标 App 编码）；
- 连续 60 分钟无累计延迟；
- output underrun 达到约定阈值，例如稳定环境下少于 1 次/10 分钟；
- 停止后 Native 与音频资源全部释放。

## 6. Phase 4：本地端口处理

任务：

- 实现 VCP/1 codec 与增量 parser；
- 实现 socket tx/rx 双线程及有限队列；
- handshake、参数、PING/PONG、错误消息；
- sequence、过期输出和 discontinuity；
- 重连与默认静音故障策略；
- 提供参考透传 server 和可注入延迟/丢帧的测试 server；
- UI 显示 server、RTT、in-flight、超时和重连次数。

退出条件：

- TCP 任意拆包/粘包下 parser 正确；
- server 处理暂停 300 ms 不导致 App OOM 或永久累计延迟；
- server 被杀后 500 ms 左右进入静音/错误提示并开始受控重连；
- 恢复后不重放断线期间旧语音；
- 外部模式 P95 目标 ≤130 ms；
- 非 loopback 地址被配置层拒绝。

## 7. Phase 5：产品 UI、部署与加固

任务：

- 完成主页、效果、外部处理、诊断和高级设置页面；
- 目标应用选择与 package→UID 刷新；
- DataStore 持久化；
- 通知静音/停止动作；
- 用户引导：“先启动变声器，再打开目标应用麦克风”；
- 自动生成 Magisk 模块；
- release 日志裁剪、混淆/JNI keep rules；
- 升级、重启、模块卸载与回滚说明；
- 隐私说明和第三方许可证清单。

退出条件：

- 新设备按文档可安装并完成自检；
- release APK + Magisk 模块的包名、签名、allowlist 一致；
- 卸载模块/停用服务后系统音频恢复；
- 无 PCM 被默认写盘或写日志；
- 所有错误都有可操作提示和诊断码。

## 8. 自动化测试规划

### 8.1 JVM 单元测试

- 状态机合法/非法迁移；
- ring buffer 满/空、回绕、丢旧策略；
- sequence UInt32 回绕比较；
- PCM mono/stereo、S16LE 编解码、限幅；
- resampler 连续状态和 discontinuity reset；
- VCP header 编解码；
- parser 拆包、粘包、非法长度、未知 type；
- reconnect/backoff 与故障策略；
- 配置校验只允许 loopback。

### 8.2 Native 测试

- 已知输入的 golden vector；
- 静音、脉冲、极值、随机噪声；
- 参数边界与 fuzz；
- AddressSanitizer/UndefinedBehaviorSanitizer（可用构建环境中）；
- 重复 create/reset/destroy；
- 不同 frame 连续性。

### 8.3 Android instrumentation

- 运行时权限流程；
- FGS 启停和通知动作；
- AudioRecord/AudioTrack 初始化失败回滚；
- 设备插拔与 Activity 重建；
- 服务与 UI 解绑后继续运行；
- DataStore 配置恢复；
- capability report 一致性。

### 8.4 真机系统测试

至少覆盖：

| 维度 | 场景 |
|---|---|
| 安装身份 | 普通 APK、priv-app + allowlist |
| 输入 | 内置、有线、USB；Bluetooth 后续 |
| 处理 | passthrough、internal、socket |
| 生命周期 | 目标 App 先开/后开麦克风、锁屏、切后台、强停 |
| 中断 | 来电、其他录音 App、隐私开关、拔耳机 |
| 故障 | server 慢/断开/非法包、DSP 异常、路由注册失败 |
| 时长 | 5 分钟功能、30 分钟回归、2 小时 soak |
| 清理 | 正常停止、异常退出、模块禁用、设备重启 |

## 9. 性能与质量验收指标

首版建议目标：

- 内部模式 App 内链路延迟 P95 ≤100 ms；
- 本地端口模式 App 内链路延迟 P95 ≤130 ms；
- 稳态队列不随运行时长增长；
- 30 分钟内存无持续上升趋势；
- 标准目标设备无持续音频爆音/周期性断裂；
- 稳定环境下 underrun 少于 1 次/10 分钟，最终按设备基线调整；
- 外部断开后约 500 ms 内进入安全静音；
- 启停 20 次后 `dumpsys media.audio_policy` 无本应用残留 mix；
- 停止后目标应用恢复真实麦克风；
- 运行中通知持续可见且一键停止有效；
- 无默认音频落盘，无非 loopback 传输。

延迟测试应使用数字标记或声学 loopback 交叉相关，报告 P50/P95/P99；不能只报告平均值。

## 10. 主要风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| 虚拟设备存在但不能供第三方录音注入 | 核心功能不可用 | Phase 1 主动标记音验证；多后端；尽早止损 |
| AudioPolicy API 为 system/hidden 且 ROM 有额外检查 | 编译或运行失败 | 版本 facade、最小 stubs、真机 SecurityException/源码核对 |
| UID/preset 无法精确匹配目标 | 影响其他录音客户端 | UI 警告、只允许单目标会话、优先 UID 规则 |
| 目标 App 已打开 AudioRecord 不会热迁移 | 用户认为无效 | 明确启动顺序，检测/提示重新开麦 |
| SELinux denial | 路由或设备 open 失败 | Enforcing 下抓日志，只加最小设备专用规则 |
| TCP/server 抖动导致延迟累计 | 通话不可用 | 有界队列、丢旧帧、过期输出丢弃、静音故障策略 |
| DSP 算法延迟/耗电高 | 音质和续航差 | 10 ms 帧、native 优化、先传统 DSP，性能门槛 |
| 第三方 DSP 许可证不兼容 | 无法发布 | 引入前审查，接口隔离便于替换 |
| Bluetooth 采样率与路由复杂 | 失真/高延迟 | 首版标实验，边界 resample，逐设备验证 |
| FGS/权限限制随 Android 版本变化 | 后台启动失败 | 用户前台启动、准确 service type、目标 API 回归 |
| 自动旁路泄露原声 | 隐私风险 | 默认静音，旁路必须显式选择 |

## 11. Definition of Done（核心版本）

只有同时满足以下条件，才可称为“第三方应用实时变声器”：

1. 在声明支持的设备/ROM 上，特权身份和权限可重复部署；
2. 目标应用数字域接收到的是处理后 PCM，而不是声学回录；
3. 内部与本地端口两种模式均能连续运行并满足延迟门槛；
4. 前台通知、用户授权、静音故障策略完整；
5. 停止/异常后系统路由可靠恢复；
6. 诊断页能区分采集失败、处理失败、注入失败和目标未重开麦克风；
7. 所有生产依赖许可证明确；
8. SELinux 保持 Enforcing；
9. 默认不录音落盘、不向非 loopback 地址发送 PCM；
10. 支持范围和不支持的 ROM/场景在 README 中如实说明。
