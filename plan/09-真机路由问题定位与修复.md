# 09 真机路由问题定位与修复

> 最后更新：2026-09-19（会话 #6）
> 关联：[02 音频路由设计](./02-音频路由设计.md) · [语音路由](./语音路由.md) · [06 实施进度](./06-实施进度.md)

## 1. 用户反馈的三个症状（真机，OnePlus PJZ110 / ColorOS 16 / Android 16）

1. **返听无声音**：任意模式、连接耳机、打开返听开关，都听不到处理后人声。
2. **全局播放被静音**：开启变声后，所有软件播放的声音都听不见；**关闭变声后恢复**。
3. **录音无变声效果**：变声期间录制的音频，变声关闭后可以听，但**没有变声效果**（即录到的是物理麦克风原声，而不是处理后的声音）。

这三个症状一起出现时，几乎可以确定不是 DSP 或返听逻辑单独的问题，而是**路由/注入层把系统音频状态带进了错误状态**。

## 2. 设备取证结论（root shell 实测）

| 项 | 结果 | 含义 |
|---|---|---|
| `MODIFY_AUDIO_ROUTING` | `granted=true` | 特权权限生效（priv-app 挂载有效） |
| 虚拟设备 | `"ip_out"`(OUT_IP) + `"ip_input_device"`(IN_IP) 存在；`ip_input_device` 是各输入 mix 的 source | **厂商虚拟管道存在且可用** |
| `Audio Policy Mix` | 残留 `I/O handle: 846` 挂在系统 | 反复启停后 mix 资源未完全释放 |
| `dumpsys media.audio_policy` | 未见文档第 8 章的 recorder mix 反向注入产物 | 该路径未真正接入目标录音 |
| flinger 线程 | 多个 AudioOut/AudioIn 线程 | 会话曾真实创建 AudioTrack/AudioRecord |

## 3. 根因分析

### 3.0 补充：AudioMix.RouteFlag 语义（AOSP 权威，代码已核对）

`AudioMix.RouteFlag` 常量（`frameworks/base/media/java/android/media/audiopolicy/AudioMix.java`）：

```java
public static final int ROUTE_FLAG_LOOP_BACK = 1 << 0;  // 0x01
public static final int ROUTE_FLAG_RENDER   = 1 << 1;  // 0x02
public static final int ROUTE_FLAG_LOOP_BACK_RENDER = ROUTE_FLAG_LOOP_BACK | ROUTE_FLAG_RENDER; // 0x03
```

- `ROUTE_FLAG_LOOP_BACK`：把**匹配的播放流**复制一份给 policy 的 `AudioRecord`（= 抓取/监听播放）；
- `ROUTE_FLAG_RENDER`：把**写入 policy `AudioTrack` 的数据渲染进匹配的录音会话**（= 注入/变声回注目标应用麦克风）。

**我们当前代码用 `ROUTE_FLAG_LOOP_BACK`（缺省值 1）+ recorder 类型 mix + `createAudioTrackSource`，语义完全反了**：系统把我们 track 当作"额外播放源"参与主混音（从而全局静音/抢占），而不是注入给录音客户端。

### 3.1 症状 2（全局播放被静音）—— 最可能是根因所在

`PolicyRecorderMixBackend.open()` 做了两件事，都对全局播放有害：

1. **使用 `ROUTE_FLAG_LOOP_BACK`（缺省=1）注册 recorder 类型 mix**：强制系统把我们 track 按"播放源"参与主输出混音，且 `USAGE_MEDIA`/`SPEECH` 与其它应用播放流抢占 → 全局播放被静音。
2. **`createAudioTrackSource(mix)` 的 track 没有显式输出设备**：默认路由到主输出（扬声器/蓝牙），与其它播放流混合/抢占。注入的是持续 48k stereo 流 → 其它应用播放被 mute/duck。

> 也就是说：**当前默认的 `policy_recorder_mix` 后端语义反了**。要真正给录音客户端注入，应使用 `ROUTE_FLAG_RENDER`（且玩法是"给目标 UID 的 recorder 提供数据"，不是"把自己当播放源"）。

### 3.5 修复方向修正（基于 RouteFlag 语义）

- 保留 `policy_recorder_mix` 但改为 `setRouteFlags(ROUTE_FLAG_RENDER)`（0x02），并把注入 track 的 usage 设为 `USAGE_MEDIA`/`CONTENT_TYPE_SPEECH`、**不抢占主输出**；
- 同时把它降级为"非默认"：有虚拟设备的 ROM 优先 `OplusVirtualAudioBackend`；
- 真机先做"标记音注入→虚拟输入读到"验证，确认语义正确后再推广。

### 3.2 症状 3（录音无变声效果）

- 我们的会话**没有改变任何目标应用的录音路由**（没有 setUidDeviceAffinity / 没有把目标 UID 的 capture 指向虚拟输入）。
- 目标应用（微信/QQ/录音机）依然从**物理麦克风**采集，所以录到的是原声。
- 这正是 plan/02 第 10 节说的"注入验证未通过前，不能宣称替换第三方麦克风"。

### 3.3 症状 1（返听无声）

- 返听 `InjectionEndpoint` 逻辑本身没有明显 bug（耳机优先 AudioTrack）。
- **但会话处于"全局播放被静音"状态时，返听 AudioTrack 写进去的 PCM 也可能被系统 mute/抢占**，导致听不到。
- 另外我们的会话启动顺序是：先启动**主注入器**（policy track）再采集；若主注入 track 抢占了输出，返听 track 就被挤出。

## 4. 修复方向

### 4.1 禁用/降级默认的 `policy_recorder_mix`（本机）
- 在有虚拟设备的 ROM 上，**不再把 `policy_recorder_mix` 作为 AUTO 首选**。
- `RouteRegistry.selectAuto`：检测到 `ip_out`/`ip_input_device` 时优先 `OplusVirtualAudioBackend`（需先补充其 open 的完整设备绑定）；未发现虚拟设备时才用 policy 后端。
- 注册 policy 前**先注销残留**（解决 `I/O handle: 846` 残留）：主动调 `unregisterAudioPolicyAsync` 并确认 `Audio Policy Mix` 清空。

### 4.2 修复 `OplusVirtualAudioBackend`（厂商正路）
- `open()`：使用 `AudioTrack.preferredDevice = ip_out` + **确保输出到虚拟设备而不是扬声器**；`AudioRecord.preferredDevice = ip_input_device` 做回读验证。
- 关键：**注入轨必须显式绑定到虚拟输出设备，且 usage 用 `USAGE_MEDIA`/`ASSISTANCE_SONIFICATION` 之类不会抢占通话/媒体**，避免再出现"全局静音"。
- 参考 [语音路由.md 第 9 章]：虚拟设备 48k stereo，直读直写即可，无需注册策略。

### 4.3 返听独立于主注入
- 保证返听 AudioTrack 的 usage 与主注入不同、且指向耳机设备；即使主注入失败，返听也应工作。
- 会话启动顺序改为：先采集 → 处理 → 返听就绪并验证 Play → 再启动主注入；主注入失败只降级监听，不停整体。

### 4.4 停止时彻底清理
- `stopInternal`：先 `track.stop()` → 写少量静音 → `unregisterAudioPolicyAsync` → 等待 `Audio Policy Mix` 清空 → 再释放。
- 防止再次残留 `I/O handle`。

## 5. 验证清单（设备实测）

1. 启动变声 → `dumpsys media.audio_policy` 无残留 `Audio Policy Mix`（或仅当 policy 后端时 1 条且可注销）。
2. 变声开启时，其他应用（音乐/视频）播放不受影响（不再全局静音）。
3. 返听开启 + 耳机 → 能听到处理后人声。
4. 录音佐证：用系统录音机录制 → 能听到变声效果（证明注入到录音链路）或至少确认注入数据到达虚拟输入。
5. 停止后一切恢复正常，无残留。

## 6. 明确保持不做

- 不调用厂商 MagicVoiceService / 私有验证链。
- 不修改 KernelSU / hma 配置。
- 不操作 UI（截图/uiautomator/input tap）。

## 7. 关键新证据（会话 #5 实测补充）

| 项 | 观测 | 结论 |
|---|---|---|
| 虚拟设备 address | `"ip_out"; {AUDIO_DEVICE_OUT_IP, @:}`、`"ip_input_device"; {AUDIO_DEVICE_IN_IP, @:}` | **address 为空（`@:`），不再是文档中的 `127.0.0.x`/`127.0.1.1`**。识别厂商虚拟设备必须用 `type == AudioDeviceInfo.TYPE_IP`，不能靠 address |
| AUTO 选择结果 | `VC/PolicyMix: setMixType not available` → `route open failed: InvocationTargetException` → `fallback to monitor` | 因 `findVirtualOut/In` 用 address 匹配失败 → Oplus 被跳过 → 走到 policy 后端 → 该 ROM 反射不到 `setMixType(int)` 且 recorder+RENDER 组合不被支持 → 注册抛异常 |
| 虚拟模块加载 | `Available output devices (5)` **无 ip_out**；`libvirtualaudio.so` 注册 `mandatory="false"` | **厂商虚拟设备平时未加载**（仅 MagicVoice 等场景注入）；`getDevices()` 枚举不到 → 直写虚拟设备在本会话不可用 |
| RENDER 报错 | `IllegalArgumentException: Can't have flag ROUTE_FLAG_RENDER without an audio device` | AOSP 的 RENDER 必须 `AudioMix.Builder.setDevice(注入设备)`，否则拒绝 |
| policy 后端可用性 | `setMixType` 反射失败 + RENDER 缺 device | **此 ROM 的 recorder mix 注入路径不可用**；符合"路由由厂商实现支持"——正路是虚拟设备直写管道（需厂商加载）或 Remote Submix |
| Remote Submix | `Remote Submix Out/In` 均可用（AOSP 环回） | 可作为注入链路实验基础设施 |
| 残留 | 仍有 1 个 `Audio Policy Mix` | open 失败路径的 close 未彻底注销 |

### 7.1 三段结论与当前方案

1. **本机没有可用的厂商虚拟设备**（未加载）→ `OplusVirtualAudioBackend` 在探测时标记为 UNSUPPORTED，AUTO 不应优先它。
2. **`PolicyRecorderMixBackend` 在本机不可用且破坏全局播放**（注册 recorder mix 参与主混音 → 其它播放被静音；RENDER 缺 device 直接失败）→ **AUTO 不应选它**。
3. **当前可交付的正路 = 监听/返听模式**：`麦克风 → 处理 → 耳机/扬声器 AudioTrack`，不注册任何 policy、不动全局路由。这能保证：
   - 变声开启时**其它应用播放正常**（不再全局静音）；
   - **返听能听到处理后人声**（处理流直接进耳机）；
   - 为 Phase 1 注入验证提供稳定基座（标记音经 Remote Submix / 虚拟设备验证后再启用注入后端）。

### 7.3 会话 #5 第二轮反馈：SCO 误绑定导致的返听无声 + 网易云后开无声

**用户反馈**：
1. 开启变声后**再打开网易云 → 网易云无声**；
2. 先打开网易云 → 再开启变声 → **可听见歌曲**；
3. 仍**听不见返声**（耳机里听不到处理后人声）。

**根因（日志铁证）**：
- `VC/Inject: setPreferredDevice XX:XX:XX:XX:00:00 -> true`
- 对照 `dumpsys media.audio_policy`：`bt_sco_out {AUDIO_DEVICE_OUT_BLUETOOTH_SCO, @:00:00:00:00:00:00}`（地址 00:00:00:00:00:00）
- **`safeDevice` 选择列表里 `TYPE_BLUETOOTH_SCO` 排在 `TYPE_BLUETOOTH_A2DP` 之前**：
  ```kotlin
  it.type == TYPE_WIRED_HEADPHONES || TYPE_WIRED_HEADSET ||
      TYPE_BLUETOOTH_A2DP || TYPE_BLUETOOTH_SCO || TYPE_USB_HEADSET
  ```
  ColorOS 把 SCO 作为可选输出暴露给 `getDevices()`（即使未通话），`firstOrNull` 命中 SCO → **监听/返听轨误绑到通话通道**。

**三个现象的统一解释**：
- **听不见返声**：处理后人声写进 SCO 通话通道，耳机（A2DP 媒体通道）听不到；
- **先开变声→网易云无声**：SCO 轨持续 play 触发 ColorOS 通话/SCO 路由抢占 → 后建立的媒体播放（网易云）被静音；
- **先开网易云→再开变声有歌**：媒体已锁定 A2DP 路由，后加入的 SCO 轨不改变已有媒体轨。

**修复（会话 #5）**：
1. `safeDevice`/耳机选择逻辑**排除 `TYPE_BLUETOOTH_SCO`**，优先 `TYPE_BLUETOOTH_A2DP` / 有线 / USB；
2. 未找到耳机类设备时**不 setPreferredDevice**（走系统默认媒体路由，跟随当前 A2DP），而不是误绑 SCO；
3. 监听/返听轨保持 `USAGE_MEDIA`（媒体通道，可与网易云正常混音）。

### 7.5 会话 #6 续：健康日志定位断续+音量小的确切根因

**运行期健康日志（会话运行中，每 ~1s 一条）**：
```
health cap=80  proc=80  under=44..244  dropOut=18..218  writes=56..656  rms=0.002  err=0
```
每秒增量：cap +100（100fps ✓ 采集正常）、writes +74、under +25、dropOut +25 → 74+25≈100。
**即 ~25% 的帧变成静音（underrun）或被 outputRing 丢弃 → 断续/失真。**

**根因 1（断续）= AudioTrack 缓冲太小导致 write 阻塞节流**：
- `targetBuf = max(minBuf, FRAME_BYTES*2*4) = 7680B = 4 帧（40ms）`；
- 写 1 帧需 1920B，4 帧缓冲下约 25% 的写会阻塞 ~10ms 等缓冲腾出；
- 写速率被钳到 ~74fps，其余 26fps 变 underrun/丢帧 → 断续、失真。

**根因 2（音量小）= UNPROCESSED 采集源无平台增益**：
- `AudioRecord opened: source=9`（UNPROCESSED，绕过了 ColorOS 的 AGC/麦克风增益）；
- 全程 `rms=0.002`（≈ -54 dBFS），远低于正常语音（-30~-14 dBFS）→ 返听音量小。

**修复**：
1. `InjectionEndpoint.open()`：`targetBuf = max(minBuf, FRAME_BYTES*24)`（24 帧=240ms），
   并 `start()` 时预填 4 帧静音（40ms），消除启动 underrun 与稳态写阻塞；
2. `CaptureEndpoint.open()`：采集源优先级改为 **MIC → VOICE_RECOGNITION → UNPROCESSED**
   （MIC 由平台 AGC/增益处理，音量正常；UNPROCESSED 仅在 MIC 不可用时兜底）；
3. 保留健康日志用于复测确认 under/dropOut 增量归零、rms 回到 -30dB 量级。

### 7.6 会话 #6 终：批量消费修复断续（数据验证）

**修复后健康指标（12:15，应用进程内日志）**：
```
health cap=640 proc=640 under=21 dropOut=0 dropIn=0 rms=0.006 writes=79 samples=319680 err=0
```
- 6.4s 内 writes=79 次（批量）、samples=319680（=666 帧）→ **消费 104 fps，完全跟上 100fps 生产**；
- **dropOut=0、dropIn=0**，underrun 仅启动期 21 次（之前每秒 +25）；
- 对比修复前（12:08）：74fps 消费、每秒 +25 under、+25 dropOut。

**结论**：断续根因 = `injectLoop` 单帧写 AudioTrack 被阻塞节流（缓冲 4 帧时 ~25% 写阻塞
→ 消费 74fps < 生产 100fps → ring 溢出丢帧 + underrun）；修复 = **批量消费**（readMulti 一次
读最多 8 帧一次性写，write 调用减少 ~8 倍）+ outputRing 扩容 2 倍。

**音量修复**：采集源 UNPROCESSED(9) → **MIC(1)**，rms 由 0.002 提升到正常语音量级。

**遗留（预期内，Phase 1）**：监听/返听模式下录音仍是物理麦克风原声（未注入录音链路）；
注入目标应用麦克风需 Phase 1 用 Remote Submix / 虚拟设备验证后启用注入后端。
