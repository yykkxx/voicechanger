# Android 语音路由能力技术详解
## —— 如何编写一个特权应用利用系统音频路由

> 本文基于 OPPO/ColorOS (Android) 真机逆向与系统探测结果整理，目标读者是希望**不使用厂商私有变声服务**、而是**自行实现音频采集/处理/回注**的开发者。

## 1. 背景：为什么不该走厂商私有接口

在 OPPO/ColorOS 设备上，系统提供了 `MagicVoiceService`（魔法语音）服务，用于游戏变声、语音回听等功能。该服务由 `com.oplus.games`（游戏空间）提供，并设有**四层防护**：

| 防护层 | 机制 | 性质 |
|---|---|---|
| 权限检查 | `com.oplus.permission.safe.GAME` / `oppo.permission.OPPO_COMPONENT_SAFE` | 签名级 |
| Java 签名校验 | `checkSignature()` / `checkSignatureWithApp()` | 调用 `PackageManager` |
| Native 签名校验 | `nativeCheckSignature()` (JNI) | 独立验证 |
| 加密握手 | `EncryptVerifyTask` + `EncryptAppHelper` | 挑战-响应协议 |

其中**加密握手层需要厂商平台私钥**，任何 Hook 方案都无法伪造。因此，试图"破解"这套验证链来使用 `MagicVoiceService` 是**死路**。

**但是**——你真正需要的"路由能力"并不在这套验证链后面。路由的物理实现位于系统最底层，是**独立的公开基础设施**。

## 2. 系统音频路由的三层架构

理解这一点是全文的关键。Android 音频栈分为三层：

```
┌─────────────────────────────────────────────────────┐
│ 应用层 (App)                                          │
│   AudioTrack / AudioRecord / MediaPlayer             │
│   AudioManager / AudioPolicy / AudioMix              │
└──────────────────────┬──────────────────────────────┘
                       │ Binder
┌──────────────────────▼──────────────────────────────┐
│ Framework 层 (system_server / audioserver)           │
│   AudioPolicyService      ← 路由决策、设备选择        │
│   AudioFlinger            ← 混音、线程管理            │
│   ★ 权限检查发生在这里 ★                              │
└──────────────────────┬──────────────────────────────┘
                       │ HIDL / AIDL
┌──────────────────────▼──────────────────────────────┐
│ HAL 层 (vendor / odm)                                │
│   audio.primary.default.so                           │
│   libvirtualaudio.so      ← 虚拟音频管道实现         │
│   ★ 这一层不做任何身份/签名校验 ★                     │
└─────────────────────────────────────────────────────┘
```

**关键认知**：厂商的验证链（`MagicVoiceService`）位于**应用层**，保护的是"调用厂商服务的入口"。而路由控制能力位于 **framework 层**，其访问控制**只依赖标准 Android 权限**，与厂商签名无关。

## 3. 路由基础设施一：厂商虚拟音频设备

在 OPPO/ColorOS 设备上，存在一套**通用的虚拟音频设备**，由 ODM 配置定义。

### 配置文件位置

```
/odm/etc/virtual_audio_policy_configuration.xml
```

### 设备定义（实测）

```xml
<module name="virtual" halVersion="3.0">
    <mixPorts>
        <mixPort name="virtual output"  role="source">
            <profile format="AUDIO_FORMAT_PCM_16_BIT"
                     samplingRates="48000" channelMasks="AUDIO_CHANNEL_OUT_STEREO"/>
        </mixPort>
        <!-- virtual output2 ~ output5 结构相同 -->
        <mixPort name="virtual input" role="sink">
            <profile format="AUDIO_FORMAT_PCM_16_BIT"
                     samplingRates="48000" channelMasks="AUDIO_CHANNEL_IN_STEREO"/>
        </mixPort>
    </mixPorts>

    <devicePorts>
        <devicePort tagName="Virtual Host Out"  type="AUDIO_DEVICE_OUT_IP" role="sink"   address="127.0.0.1">
        <devicePort tagName="Virtual Host Out2" type="AUDIO_DEVICE_OUT_IP" role="sink"   address="127.0.0.2">
        <devicePort tagName="Virtual Host Out3" type="AUDIO_DEVICE_OUT_IP" role="sink"   address="127.0.0.3">
        <devicePort tagName="Virtual Host Out4" type="AUDIO_DEVICE_OUT_IP" role="sink"   address="127.0.0.4">
        <devicePort tagName="Virtual Host Out5" type="AUDIO_DEVICE_OUT_IP" role="sink"   address="127.0.0.5">
        <devicePort tagName="Virtual Host In"   type="AUDIO_DEVICE_IN_IP"  role="source" address="127.0.1.1">
    </devicePorts>

    <routes>
        <route type="mix" sink="Virtual Host Out" sources="virtual output"/>
        <route type="mix" sink="Virtual Host In"  sources="Virtual Host In"/>
    </routes>
</module>
```

### HAL 实现

```
/odm/lib64/hw/libvirtualaudio.so
```

注册方式（见 `/vendor/etc/audio/vendor_audio_interfaces.xml`）：

```xml
<library name="virtual_audio"
         libraryName="/odm/lib64/hw/libvirtualaudio.so"
         method="registerIModuleVirtualAudio"
         mandatory="false"/>
```

### ★ 最重要的验证结果

对 `libvirtualaudio.so` 做字符串扫描，**没有发现任何**以下内容：

```
permission / package / uid / denied / forbidden / whitelist / signature / checkPkg
```

**这意味着：HAL 层是纯管道实现（pipe），只负责搬运 PCM 数据，不做任何身份校验。**

同时，XML 配置文件中也**没有** `whitelist` / `allowlist` / 包名限制条目。

> 结论：限制**不在** HAL 层，**不在** XML 层，而在 framework 的权限层（见第 5 节）。

## 4. 路由基础设施二：AOSP Remote Submix

除了厂商虚拟设备，Android 原生还提供 **Remote Submix** 机制。

### 配置

```
/vendor/etc/r_submix_audio_policy_configuration.xml
```

```xml
<devicePort tagName="Remote Submix Out" type="AUDIO_DEVICE_OUT_REMOTE_SUBMIX" role="sink">
<devicePort tagName="Remote Submix In"  type="AUDIO_DEVICE_IN_REMOTE_SUBMIX"  role="source">
```

对应设备常量：

- 输出：`AUDIO_DEVICE_OUT_REMOTE_SUBMIX`
- 输入：`AUDIO_DEVICE_IN_REMOTE_SUBMIX`

这是一条**环路（loopback）通道**：任何路由到 `OUT_REMOTE_SUBMIX` 的音频，都能从 `IN_REMOTE_SUBMIX` 读到。常用于屏幕录制、音频转发。

## 5. 权限模型：限制发生在哪一层

这是全文最核心的部分。在真机上用 `dumpsys package` 实测各音频权限的**保护级别（protectionLevel）**：

| 权限 | 保护级别 | 说明 |
|---|---|---|
| `android.permission.MODIFY_AUDIO_ROUTING` | `signature\|privileged\|role` | 修改音频路由 |
| `android.permission.CAPTURE_AUDIO_OUTPUT` | `signature\|privileged\|role` | 捕获音频输出 |
| `android.permission.MODIFY_AUDIO_SETTINGS` | `normal` | 修改音频设置 |
| `android.permission.RECORD_AUDIO` | `dangerous` | 录音（运行时申请） |
| `com.oplus.permission.safe.GAME` | `signature\|privileged` | 厂商游戏权限 |
| `oppo.permission.OPPO_COMPONENT_SAFE` | `signature`（纯签名） | 厂商组件保护 |

### 关键判断

保护级别中的 `privileged` 是一个**独立的授权通道**。它的含义是：

> **只要应用被安装在特权分区（`/system/priv-app/`），系统就自动授予该权限，无论签名是否匹配。**

因此：

- `MODIFY_AUDIO_ROUTING` 和 `CAPTURE_AUDIO_OUTPUT` 带 `privileged` → **特权应用可自动获得** ✅
- `oppo.permission.OPPO_COMPONENT_SAFE` 是纯 `signature` → **无法通过特权绕过** ❌

**这正是你与厂商验证链的根本区别：**

| 路径 | 需要的条件 | 你是否满足 |
|---|---|---|
| 厂商私有接口 (`MagicVoiceService`) | 纯签名校验 + 平台私钥 | ❌ 无法满足 |
| 系统标准路由 API | `privileged`（特权分区） | ✅ 可以满足 |

## 6. 特权应用的判定与授予机制

### 6.1 什么是特权应用

`PackageManagerService` 在扫描 APK 时，根据**安装目录**判定应用等级：

| 目录 | 等级 | 可获得权限 |
|---|---|---|
| `/data/app/` | 普通应用 | `normal` / `dangerous` |
| `/system/app/` | 系统应用 | 额外获得部分系统权限 |
| `/system/priv-app/` ★ | **特权应用** | `signature\|privileged` 均可得 |
| `/system_ext/priv-app/` ★ | **特权应用** | 同上 |
| `/vendor/priv-app/` ★ | **特权应用** | 同上 |
| `/product/priv-app/` ★ | **特权应用** | 同上 |
| `/odm/priv-app/` ★ | **特权应用** | 同上 |

**只有 `priv-app` 目录下的应用才被称为 privileged app。**

### 6.2 授予判定逻辑（简化自 PMS 源码）

```
扫描 /system/priv-app/xxx/xxx.apk
  → 解析 AndroidManifest.xml
  → 读取 <uses-permission> 列表
  → 对每个权限，查询 PermissionInfo.protectionLevel
  → if (protectionLevel & PROTECTION_FLAG_PRIVILEGED) && 应用在 priv-app
        → 直接授予 (granted=true)
  → if (protectionLevel == signature)
        → 比对应用签名与权限声明者签名
        → 匹配才授予
```

所以，被赋予 privileged 权限的特权应用，其权限在 `dumpsys package` 中会显示 `: granted=true`。

### 6.3 特权应用清单要求

除了目录位置，还有一个容易被忽略的点：**`/system/etc/permissions/` 下的 XML 白名单**。

某些特权权限需要在系统权限白名单中显式声明包名，例如：

```xml
<!-- /system/etc/permissions/privapp-permissions-platform.xml -->
<permissions>
    <privapp-permissions package="com.your.app">
        <permission name="android.permission.MODIFY_AUDIO_ROUTING"/>
        <permission name="android.permission.CAPTURE_AUDIO_OUTPUT"/>
    </privapp-permissions>
</permissions>
```

> **注意**：自 Android 9 起，如果一个 privileged 应用申请了 `signature|privileged` 权限但**未列入白名单**，系统会在启动时抛出错误（部分 ROM 是警告）。因此，**通过 Magisk 挂载时，务必同时提供对应的权限白名单 XML**。

## 7. 实战：编写一个特权应用

### 7.1 AndroidManifest.xml

```xml
<?xml version="1.0" encoding="utf-8"?>
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
    package="com.example.audiorouter">

    <!-- ★ 特权权限：需要 privileged 分区 -->
    <uses-permission android:name="android.permission.MODIFY_AUDIO_ROUTING"/>
    <uses-permission android:name="android.permission.CAPTURE_AUDIO_OUTPUT"/>
    <uses-permission android:name="android.permission.MODIFY_AUDIO_SETTINGS"/>

    <!-- 普通权限 -->
    <uses-permission android:name="android.permission.RECORD_AUDIO"/>
    <uses-permission android:name="android.permission.FOREGROUND_SERVICE"/>

    <!-- ★ 关键：标记为系统/特权应用 -->
    <application
        android:label="Audio Router"
        android:persistent="true"
        android:directBootAware="true">

        <service
            android:name=".AudioRouterService"
            android:exported="false"/>

    </application>
</manifest>
```

### 7.2 编译

使用标准 Android 构建（Gradle）。构建出 APK 后，**不要把 app 装到 `/data/app`**，而是通过第 10 节的 Magisk 方式挂载到 `priv-app`。

### 7.3 验证是否成为特权应用

安装/挂载后，执行：

```bash
# 确认安装位置
pm path com.example.audiorouter
# 期望输出: package:/system/priv-app/AudioRouter/AudioRouter.apk

# 确认权限已授予
dumpsys package com.example.audiorouter | grep -E "MODIFY_AUDIO_ROUTING|CAPTURE_AUDIO_OUTPUT"
# 期望输出:
#   android.permission.MODIFY_AUDIO_ROUTING: granted=true
#   android.permission.CAPTURE_AUDIO_OUTPUT: granted=true

# 确认 packageFlags
dumpsys package com.example.audiorouter | grep flags
# 期望包含: SYSTEM  PRIVILEGED
```

若 `granted=true` 且 flags 含 `PRIVILEGED`，则特权身份建立成功。

## 8. 实战：注册 AudioPolicy + AudioMix

这是**最推荐**的路由方式：通过 `AudioMix` 把指定音频环路（loopback）复制一份给你处理，然后你自己回注。

### 8.1 核心概念

- **AudioPolicy**：你向系统注册的一个音频策略
- **AudioMix**：策略中的一条规则，描述"匹配哪些音频 + 如何路由"
- **ROUTE_FLAG_LOOP_BACK**：在原有播放链路之外，**额外复制一份** PCM 给你的 `AudioRecord`

### 8.2 代码实现

```kotlin
import android.content.Context
import android.media.AudioAttributes
import android.media.AudioFormat
import android.media.AudioManager
import android.media.AudioRecord
import android.media.audiopolicy.AudioMix
import android.media.audiopolicy.AudioMixingRule
import android.media.audiopolicy.AudioPolicy
import android.util.Log

class AudioRouter(context: Context) {

    private val audioManager =
        context.getSystemService(Context.AUDIO_SERVICE) as AudioManager
    private var audioPolicy: AudioPolicy? = null
    private var captureRecord: AudioRecord? = null

    /** 注册一条 LOOP_BACK 混音：捕获所有 USAGE_GAME 的音频 */
    fun startCapture() {
        // 1. 定义捕获格式
        val format = AudioFormat.Builder()
            .setEncoding(AudioFormat.ENCODING_PCM_16BIT)
            .setSampleRate(48000)
            .setChannelMask(AudioFormat.CHANNEL_IN_STEREO)
            .build()

        // 2. 定义匹配规则：匹配游戏音频
        val rule = AudioMixingRule.Builder()
            .addRule(
                AudioAttributes.Builder()
                    .setUsage(AudioAttributes.USAGE_GAME)
                    .build(),
                AudioMixingRule.RULE_MATCH_ATTRIBUTE_USAGE
            )
            .build()

        // 3. 构造 AudioMix，使用 LOOP_BACK 路由
        val mix = AudioMix.Builder(rule)
            .setFormat(format)
            .setRouteFlags(AudioMix.ROUTE_FLAG_LOOP_BACK)   // ★ 关键
            .build()

        // 4. 构造 AudioPolicy
        val policy = AudioPolicy.Builder(context)
            .addMix(mix)
            .build()

        // 5. 注册（需要 MODIFY_AUDIO_ROUTING）
        val result = audioManager.registerAudioPolicy(policy)
        if (result != AudioManager.SUCCESS) {
            throw IllegalStateException("registerAudioPolicy failed: $result")
        }
        audioPolicy = policy
        Log.i("AudioRouter", "AudioPolicy registered OK")

        // 6. 从 policy 拿到 AudioRecord sink
        captureRecord = policy.createAudioRecordSink(mix)
        captureRecord?.startRecording()

        // 7. 读取 PCM 并自行处理
        readLoop(captureRecord!!)
    }

    /** 读取 PCM 数据（这里原样透传，实际可做变声/混音） */
    private fun readLoop(record: AudioRecord) {
        val buffer = ShortArray(4096)
        Thread {
            while (true) {
                val n = record.read(buffer, 0, buffer.size)
                if (n <= 0) continue
                val processed = process(buffer, n)
                writeBack(processed)
            }
        }.start()
    }

    private fun process(input: ShortArray, len: Int): ShortArray {
        // 自定义音频处理逻辑
        return input.copyOf(len)
    }

    private fun writeBack(data: ShortArray) {
        // 通过 AudioTrack 回注到虚拟设备（见第 9 节）
    }
}
```

### 8.3 其他 RouteFlag

| Flag | 含义 |
|---|---|
| `ROUTE_FLAG_LOOP_BACK` | 复制一份音频给你，原播放链路不受影响 |
| `ROUTE_FLAG_RENDER` | 用你的输出**替换**原音频 |
| `ROUTE_FLAG_LOOP_BACK_RENDER` | 两者皆需要（很少用） |

## 9. 实战：使用虚拟音频设备

除了 AudioMix，你还可以直接操作虚拟设备，实现"**写进去 → 从另一头读出来**"的管道效果。

### 9.1 枚举虚拟设备

```kotlin
// 获取所有输入设备
val inputs = audioManager.getDevices(AudioManager.GET_DEVICES_INPUTS)
inputs.forEach { dev ->
    Log.d("AudioRouter", "IN  id=${dev.id} type=${dev.type} " +
        "name=${dev.productName} addr=${dev.address}")
}

// 获取所有输出设备
val outputs = audioManager.getDevices(AudioManager.GET_DEVICES_OUTPUTS)
outputs.forEach { dev ->
    Log.d("AudioRouter", "OUT id=${dev.id} type=${dev.type} " +
        "name=${dev.productName} addr=${dev.address}")
}
```

寻找目标：

```kotlin
// 虚拟输入：address 形如 "127.0.1.1"
val virtualIn = inputs.firstOrNull {
    it.address?.startsWith("127.0.1") == true
}

// 虚拟输出：address 形如 "127.0.0.x"
val virtualOut = outputs.firstOrNull {
    it.address?.startsWith("127.0.0") == true
}
```

> 说明：虚拟设备的 `type` 在不同 ROM 上可能报告为 `TYPE_IP` 或厂商自定义值，**建议用 `address` 字段（`127.0.0.x` / `127.0.1.1`）辅助识别**，比 `type` 更可靠。

### 9.2 写入虚拟设备（AudioTrack）

```kotlin
val format = AudioFormat.Builder()
    .setEncoding(AudioFormat.ENCODING_PCM_16BIT)
    .setSampleRate(48000)
    .setChannelMask(AudioFormat.CHANNEL_OUT_STEREO)
    .build()

val track = AudioTrack.Builder()
    .setAudioFormat(format)
    .setTransferMode(AudioTrack.MODE_STREAM)
    .setBufferSizeInBytes(4096 * 4)
    .build()

// ★ 把输出重定向到虚拟设备
virtualOut?.let { track.preferredDevice = it }

track.play()
track.write(pcmData, 0, pcmData.size)
```

### 9.3 从虚拟设备读取（AudioRecord）

```kotlin
val inFormat = AudioFormat.Builder()
    .setEncoding(AudioFormat.ENCODING_PCM_16BIT)
    .setSampleRate(48000)
    .setChannelMask(AudioFormat.CHANNEL_IN_STEREO)
    .build()

val record = AudioRecord.Builder()
    .setAudioFormat(inFormat)
    .setBufferSizeInBytes(4096 * 4)
    .build()

// ★ 把输入绑定到虚拟设备
virtualIn?.let { record.preferredDevice = it }

record.startRecording()
val buf = ShortArray(4096)
record.read(buf, 0, buf.size)
```

### 9.4 两种方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| **AudioPolicy + AudioMix** | 标准 API，可控性强，可精确匹配 usage | 需要 `MODIFY_AUDIO_ROUTING` | 捕获/替换特定应用音频 |
| **虚拟设备直读直写** | 简单，无需注册策略 | 设备枚举可能因 ROM 而异 | 音频管道转发 |

### 10.5 SELinux 处理

你的设备处于 `Enforcing` 模式。特权应用运行在独立的 SELinux domain（通常是 `priv_app`）。它访问音频服务需要相应的策略规则。

**大多数情况下无需额外处理**——`priv_app` domain 通常已有访问 audioserver 的规则。

如果遇到 `avc: denied`（用以下命令查看）：

```bash
# 查看近期音频相关拒绝日志
dmesg | grep avc | grep -iE "audio|priv_app"
# 或
logcat | grep avc
```

若确实被拒，需要补充 sepolicy。Magisk 方式：

```
/data/adb/modules/audio_router/sepolicy.rule
```

内容示例（仅供参考，需根据实际 denial 调整）：

```
allow priv_app audioserver_service:service_manager find;
allow priv_app audio_device:chr_file { read write open ioctl };
allow priv_app audio_prop:file { read open map };
```

> **警告**：修改 sepolicy 有风险，务必备份，并确保规则最小化。错误的规则可能导致系统无法启动。

## 12. 附录：完整代码骨架

### 12.1 主服务

```kotlin
package com.example.audiorouter

import android.app.Service
import android.content.Context
import android.content.Intent
import android.content.pm.PackageManager
import android.media.*
import android.media.audiopolicy.*
import android.os.IBinder
import android.util.Log

class AudioRouterService : Service() {

    companion object {
        private const val TAG = "AudioRouter"
        private const val SAMPLE_RATE = 48000
    }

    private lateinit var audioManager: AudioManager
    private var audioPolicy: AudioPolicy? = null
    private var captureRecord: AudioRecord? = null
    private var playbackTrack: AudioTrack? = null
    private var running = false

    override fun onCreate() {
        super.onCreate()
        audioManager = getSystemService(Context.AUDIO_SERVICE) as AudioManager

        // 第 1 步：检查权限
        if (!hasRoutingPermission()) {
            Log.e(TAG, "缺少 MODIFY_AUDIO_ROUTING，请挂载到 priv-app")
            return
        }

        // 第 2 步：注册 AudioPolicy
        setupLoopbackMix()

        // 第 3 步：准备回注通道
        setupPlayback()
    }

    private fun hasRoutingPermission(): Boolean =
        checkSelfPermission("android.permission.MODIFY_AUDIO_ROUTING") ==
            PackageManager.PERMISSION_GRANTED

    /** 注册 LOOP_BACK 混音，捕获游戏音频 */
    private fun setupLoopbackMix() {
        val format = AudioFormat.Builder()
            .setEncoding(AudioFormat.ENCODING_PCM_16BIT)
            .setSampleRate(SAMPLE_RATE)
            .setChannelMask(AudioFormat.CHANNEL_IN_STEREO)
            .build()

        val rule = AudioMixingRule.Builder()
            .addRule(
                AudioAttributes.Builder()
                    .setUsage(AudioAttributes.USAGE_GAME)
                    .build(),
                AudioMixingRule.RULE_MATCH_ATTRIBUTE_USAGE
            )
            .build()

        val mix = AudioMix.Builder(rule)
            .setFormat(format)
            .setRouteFlags(AudioMix.ROUTE_FLAG_LOOP_BACK)
            .build()

        val policy = AudioPolicy.Builder(this)
            .addMix(mix)
            .build()

        val result = audioManager.registerAudioPolicy(policy)
        if (result != AudioManager.SUCCESS) {
            Log.e(TAG, "registerAudioPolicy failed: $result")
            return
        }
        audioPolicy = policy
        captureRecord = policy.createAudioRecordSink(mix)
        Log.i(TAG, "AudioPolicy registered")
    }

    /** 准备回注 AudioTrack（写到虚拟设备） */
    private fun setupPlayback() {
        val format = AudioFormat.Builder()
            .setEncoding(AudioFormat.ENCODING_PCM_16BIT)
            .setSampleRate(SAMPLE_RATE)
            .setChannelMask(AudioFormat.CHANNEL_OUT_STEREO)
            .build()

        playbackTrack = AudioTrack.Builder()
            .setAudioFormat(format)
            .setTransferMode(AudioTrack.MODE_STREAM)
            .setBufferSizeInBytes(SAMPLE_RATE * 4)   // ~250ms
            .build()

        // 绑定到虚拟输出设备
        findVirtualOutput()?.let { playbackTrack?.preferredDevice = it }
    }

    private fun findVirtualOutput(): AudioDeviceInfo? =
        audioManager.getDevices(AudioManager.GET_DEVICES_OUTPUTS)
            .firstOrNull { it.address?.startsWith("127.0.0") == true }

    private fun findVirtualInput(): AudioDeviceInfo? =
        audioManager.getDevices(AudioManager.GET_DEVICES_INPUTS)
            .firstOrNull { it.address?.startsWith("127.0.1") == true }

    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        if (!running) startPipeline()
        return START_STICKY
    }

    /** 主循环：读取 → 处理 → 回注 */
    private fun startPipeline() {
        val record = captureRecord ?: return
        val track = playbackTrack ?: return

        running = true
        record.startRecording()
        track.play()

        Thread({
            val buf = ShortArray(2048)
            while (running) {
                val n = record.read(buf, 0, buf.size)
                if (n <= 0) continue

                // ★ 自定义处理：变声 / 混音 / 特效
                val out = process(buf, n)

                track.write(out, 0, out.size)
            }
        }, "audio-pipeline").start()
    }

    private fun process(input: ShortArray, len: Int): ShortArray {
        // TODO: 实现你的音频算法
        return input.copyOf(len)
    }

    override fun onDestroy() {
        running = false
        captureRecord?.stop()
        captureRecord?.release()
        playbackTrack?.stop()
        playbackTrack?.release()
        audioPolicy?.let { audioManager.unregisterAudioPolicyAsync(it) }
        super.onDestroy()
    }

    override fun onBind(intent: Intent?): IBinder? = null
}
```

## 总结

| 问题 | 答案 |
|---|---|
| 路由能力在哪里？ | framework 层，由 `MODIFY_AUDIO_ROUTING` 等标准权限守护 |
| 是否受厂商签名限制？ | **否**。厂商验证链只保护私有服务入口，与路由基础设施解耦 |
| 需要什么？ | privileged 身份（`priv-app`）+ 对应权限白名单 |
| 怎么获得？ | Magisk 挂载 APK 到 `system/priv-app/` + 提供 `privapp-permissions` XML |
| HAL 层会拦我吗？ | **不会**。`libvirtualaudio.so` 无任何身份校验，是纯管道 |
| 推荐方案？ | 优先 `AudioPolicy + AudioMix (ROUTE_FLAG_LOOP_BACK)` |
| 主要风险？ | SELinux 策略（通常无需处理）、ROM 差异导致设备枚举不同 |

**一句话**：把应用挂进 `priv-app` 拿到 privileged 权限，然后用标准 AOSP 音频路由 API，就绕开了整个厂商验证体系。你只需要处理自己的音频算法和可能的 SELinux 细节。
